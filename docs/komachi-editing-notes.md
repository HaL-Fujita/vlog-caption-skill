## 今回の2本に使った設定

以下は 1080×1920、30fps の試作設定。ほかの素材では人物と TikTok の操作ボタン・説明欄を見て位置を調整する。名前や紹介文を別の出演者へそのまま流用しない。

| 要素 | 今回の設定 |
| --- | --- |
| 左上ロゴ | `MIX小町 ~Road to LAS VEGAS~`。桜色の筆文字風・小さな桜を添えた透過 PNG |
| ロゴの配置 | 左上 `(48, 52)`、表示サイズ `360×120`。全編固定。背景パネルなし |
| 紹介1行目 | `最弱から頂点を目指す`、白、Noto Sans CJK Regular 38px |
| 紹介2行目 | `ゆずひめ`、桜色、Noto Serif CJK Bold 76px |
| 紹介の表示時間 | 編集後の `0.35 ≤ t < 4.85` 秒（冒頭の約4.5秒） |
| 紹介の背景・枠 | 不透明 `#241C23`（alpha 255）、桜色の細枠 2px、角丸 5px |
| 紹介の配置 | 会話字幕の下。パネル `(170, 1328)`〜`(830, 1540)`、文字の中心 x=500 |
| 会話字幕 | 中心 `(500, 1190)`、通常 64px／聞き手 56px／強調 72px。最大2行、文字幅目安 840px |
| 章見出し | 桜色 74px、中心 `(500, 264)`。章頭から2.5秒。ロゴと重ならない位置 |
| 書き出し | H.264 / AAC、yuv420p、BT.709、tv range、`+faststart` |

ロゴは生成した透過画像を使い、紹介文は Pillow で描画した。元のロゴ素材と合成用 PNG は Git に含めず、素材フォルダで管理する。同じロゴを再利用するときは、画像を再生成する前に既存素材を探す。

## 編集と音声の扱い

- 長い無音を詰め、意味と自然な息継ぎを残した。章数や動画の尺は先に固定しない。
- BGM は声を優先し、発話中のダッキングと短いフェードを使用。今回の BGM 単体の準備では約 -34 LUFS を出発点にした。素材ごとに調整する。
- 元動画の音声で文字起こしを行い、固有名詞やポーカー用語の不明箇所は編集計画に確認事項として残す。音声認識の推測だけで確定しない。
- ロゴ・紹介を追加した再書き出しでは、カット済み映像から字幕を再合成し、直前の完成品の AAC を `-c:a copy` で引き継いだ。BGM・会話を再ミックスして音量を変えないため。
- 1本目は約36.63秒（1099フレーム）、2本目は81.6秒（2448フレーム）。
- 両方の全編デコード、字幕の幅・禁則処理、代表フレームの見た目、映像と音声の長さを確認した。
- 再書き出し前後の AAC データとデコード音声のハッシュ一致を確認。納品フォルダ20ファイルのハッシュと ZIP の CRC も検証済み。
- 実際に音声を聞けない環境では、ASR や音量測定を「試聴済み」と表現しない。

## スマホへの受け渡しで分かったこと

1. ユーザーは元動画と同じ階層の新規フォルダへの保存を希望し、その後、別の Drive 保存先を指定した。具体的な保存先 URL は会話またはリポジトリ外の記録を参照する。
2. Drive 連携を設定したとの返答があっても、今回の実行環境には書き込みツール・認証がなかった。権限の再承認だけでは解決しない状態だった。
3. `/workspace/...` のリンクも `sandbox:/workspace/...` のリンクも、ユーザーのスマホではタップして反応しなかった。ファイル名を英数字に変えるだけでは解決しなかった。
4. ユーザーの明示了承を得て、Filebin に完成 MP4 2本をアップロードした。Drive への保存完了とは扱わない。
5. 実際の HTTPS 共有 URL から2本とも全データを取得し、元ファイルとの SHA-256 一致を確認して渡した。ユーザーから受け取り成功の返答があった。

Filebin を許可された範囲で再利用する場合の要点：

- 共有 URL を知る人が閲覧できる一時保存。恒久保管先として扱わない。新しい素材にも過去の許可が自動で適用されると決めつけない。
- API はサービスの `/api`・`/api.yaml` で確認する。ランダムな bin ID を使い、`POST /{bin}/{filename}` にファイル本体を送る。`Content-Length` と `Content-SHA256` を付けて照合する。
- メタデータは `GET /{bin}` に `Accept: application/json` を付けて取得する。空の bin では `files` が `null` になる場合があった。
- アップロード応答のサイズ・SHA-256 と、実際にダウンロードしたデータの両方を確認する。応答の `expired_at` を読んで期限を案内する（今回は案内上約6日間）。
- 初回のダウンロードでは確認ページが表示される。ブラウザでは `Proceed to download` を選ぶ。API では公式ドキュメントどおり Cookie を保持して次のリクエストを行う。
- 短時間で期限切れになるリダイレクト先 URL ではなく、Filebin の共有ページ URL を渡す。アプリでタップできない場合は、URL をコピーして Safari / Chrome で開く方法を添える。
- 具体的な bin ID・共有 URL・Drive URL・認証情報はリポジトリに残さない。

## 準備済みクラウド環境での再開

以下は今回の環境の配置。別の環境では存在を確認してから使う。Git のクローンだけで個別素材まで復元されるわけではない。

```bash
cd /workspace/vlog-caption-skill
export PATH=/workspace/vlog-caption-env/venv/bin:$PATH
export XDG_DATA_HOME=/workspace/vlog-caption-env/share
export PYTHONDONTWRITEBYTECODE=1
python -m pytest -q -p no:cacheprovider
python scripts/caption_overlay_template.py --verify
```

- Python 3.12、Pillow、BudouX、FFmpeg / ffprobe と Noto CJK フォントを使用。初期設定・起動手順はクラウド環境設定にも保存済み。
- テンプレートの macOS 用フォント名は、XDG のフォントディレクトリ内のリンクで Noto Sans CJK Bold に解決している。Hiragino そのものではなく、見た目は macOS と異なる。
- 既存チェックは3テスト成功、`overflow_problems: 0` が目安。`--verify` は問題を表示する方式なので終了コードだけで判断しない。
- この作業は常駐サーバーを必要としない。プライベートな素材・編集計画・書き出しはリポジトリ外に置く。

同じ環境に残っていれば、次の場所から再開できる：

| 場所 | 内容 |
| --- | --- |
| `/workspace/komachi-video` | 1本目の素材、編集計画、ロゴ追加前の完成品 |
| `/workspace/komachi-video-02` | 2本目の素材、編集計画、ロゴ追加前の完成品 |
| `/workspace/komachi-yuzuhime-trial` | ロゴ・紹介の設定、個別レンダリング・梱包・アップロードスクリプト、検証記録 |
| `/workspace/komachi-yuzuhime-trial/小町_ゆずひめ_ロゴ紹介試作` | 最終 MP4 2本、確認画像、ロゴ・紹介 PNG |
| `/workspace/downloads` | 受け渡し用の英数字名のコピー |

作業状態は `trial-status.json`、共有先と期限は `filebin-delivery.json`、具体的なレイアウトは `overlay-design.json` に保存している。これらはリポジトリ外のローカル記録。素材が見つからない場合は、Git 内に存在すると仮定せず、会話で指定された保管先を確認する。
